FIX 1 - THE DETECTOR MEASURES INK, NOT THE PRINTED BOX
--------------------------------------------------------------------------------

scan_align.py:267 ink_fill_ratio() did:

    gray = ImageOps.autocontrast(crop.convert('L'))
    dark = sum(1 for p in gray.getdata() if p < 88)
    return dark / len(pixels)

Two separate reasons that has no discriminating power:

  * The crop is framed on the printed box, so the outline is inside the
    measurement. On a box about 28 px across the outline is a fifth of the
    pixels on its own.
  * autocontrast stretches the crop's own range, so on a box with NO ink the
    printed outline is pushed down to pure black. It manufactures a tick out
    of an empty box.

Now:

  * Ink is counted only in an INSET region, CHECKBOX_INSET = 0.28 of each
    side, which leaves roughly an 8 px margin on a 28 px box - wider than the
    +/-3 px alignment residual measured in Phase 0. The printed outline can no
    longer reach the measured area.
  * The cutoff comes from the box's OWN paper level (85th percentile of the
    crop, times 0.6, floor 40) instead of a stretched contrast, so a dim or
    WhatsApp-compressed photo is judged against its own paper.
  * Where the matching page of the official blank is available it is passed in
    as a reference and ink already printed at that spot is discounted. The
    blank's ink is grown by one pixel first (MinFilter) so a small alignment
    residual cannot leave a sliver of outline looking like a pen stroke.

Result on the pristine blanks, with NO reference (so this is the inset fix
measured on its own):

    all 69 checkboxes that carry a target now measure exactly 0.0000

The 7 remaining boxes are on CW 05 and carry NO target and NO group. Their
atlas boxes have landed on printed text rather than on a checkbox - the crops
are 25x13 and 40x16 pixels of the words "No", "Yes", "Open file",
"Emergency", "High", "Mild". No ink-based detector can call those empty,
because there is real ink in them; the boxes are simply in the wrong place.
That is atlas geometry, which this phase was told not to touch. They cannot
write to a household field. With the blank supplied as a reference they read
empty, and both facts are pinned by tests.

FIX 2 - A TICK GROUP RESOLVES TO THE BOX THAT CARRIES THE MARK
--------------------------------------------------------------------------------

scan_ocr.py:373-401 _merge_extracted() did `by_target[target] = item` for every
atlas field. All four race boxes carry target caregiver.race, so the fourth
overwrote the first three and the group became a constant.

The full group list, confirmed against form_atlas.py:

  c01           caregiver.id_type          SA ID Number / Passport Number / Permit
                caregiver.headship_type    6 options
                caregiver.nationality      South African / Other
                caregiver.sex              Male / Female
                caregiver.race             African / White / Coloured / Indian
                caregiver.marital_status   6 options
                caregiver.disability       false / true
                member.0-3 .id_type        3 options each
                member.0-3 .sex            2 options each
                member.0-3 .race           4 options each
                member.0-3 .disability     2 options each
  process_note  process_note.type_of_engagement   6 options
  intake        7 boxes with no group and no target (see above)

  C02 and C03 have NO checkbox geometry at all, which is why the three
  c02/c03 fixtures produce no checkbox output before or after this change.
  That is the Phase 0 atlas-coverage finding, not a detection bug, and it is
  also why the end-to-end tick test uses c01_household.jpg rather than
  c03_ticks.jpg - c03_ticks.jpg has real ticks on the paper but the atlas has
  no boxes to read them from.

Now a new _resolve_option_groups() collapses each group to ONE field before
the merge:

    exactly one marked, no faint boxes  -> that option, confidence 0.8
    exactly one marked, a faint sibling -> that option, flagged, note
                                           "one box is too faint to be sure"
    two or more marked                  -> BLANK, flagged,
                                           note "N boxes are marked"
    none marked, one unreadable         -> BLANK, flagged,
                                           note "no box could be read as marked"
    none marked at all                  -> BLANK, flagged, note "no box is marked"

The per-box tick evidence travels on private keys (_tick, _ink) and is
stripped by the resolver, so it never reaches the stored page or the browser
(verified: no key beginning with an underscore appears in the API payload).

The resolved field carries `options` (the whole group) and `option` (the one
chosen), so the review canvas can still offer the other answers.

_merge_extracted no longer lets declaration order decide anything. Where two
atlas boxes claim one target it ranks them explicitly (_atlas_priority): a
resolved tick group beats a free-text box, and a box with a value beats an
empty one. This matters in exactly one place today - C01 puts a free-text
"Describe" box on caregiver.nationality, the target its tick group already
owns, and that box was reading the word fragment "= hai" off the paper.

FRONTEND
--------------------------------------------------------------------------------

frontend/src/pages/ScanIntake.js - one field now represents a whole group, so:

  * fieldsToValues / mergeValuesIntoFields understand a group field (one that
    carries an `options` array) and its chosen option. Without this the staff
    member could no longer change a group's answer on the review canvas: the
    canvas sets values[target] to the option it was clicked on, and the old
    per-option matching would have thrown that away.
  * The canvas low-confidence lookup falls back to matching by target, so when
    a group could not be read EVERY box in that group is flagged amber for a
    look, not just the one that happened to win.
