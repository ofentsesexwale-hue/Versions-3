1. C02 / C03 PERSON TARGETING
================================================================================

C03 (child beneficiary)
-----------------------
Was: name / surname / ID wrote caregiver.* even though the sheet is the child
page. Phase 1 stopped a C03 in the same job as C02 from overwriting the adult,
but a C03-only scan still created a caregiver row.

Now: atlas targets are member.0.name / member.0.surname / member.0.id_number.
At save, resolve_buckets allocates a real member slot:

  * match an existing household member by SA ID
  * else match a member.N.id_number already in this job (C01 children)
  * else the next unused slot (0 on an empty file)

A C03-only scan therefore creates a HouseholdMember, not a Caregiver.

C02 (adult assessment) — reviewed, not retargeted
-------------------------------------------------
C02 stays caregiver.*. It is the adult assessment of the C01 head of
household, not an extra adult member. Evidence in this codebase:

  * Phase 1 PERSON_SUBJECT_BY_FORM maps c02 → 'adult' with c01 and CW 05
  * C01 already lists other household members as member.0–3
  * C01 + C02 for the same adult still merge onto the caregiver

Household assembly (Phase 0 / Phase 1)
--------------------------------------
C03 identity is no longer held_back when an adult sheet is in the same job.
C02 writes the caregiver; C03 writes a member. Two children in one job take
two slots.

Migration safety
----------------
Already-saved caregiver rows are not rewritten into members.

  * If a C03 page still has the old caregiver.* field names, those values
    are written to a member (needs_review reason c03_targets_rewritten).
  * If that identity is already on the household's caregiver (same ID or
    same name+surname from a pre-Phase-6 save), nothing is moved and
    nothing is written. needs_review reason legacy_c03_on_caregiver.

2. CLOSED-VOCABULARY GEOGRAPHIC MATCHING
================================================================================

After OCR, household.province / district / town are compared to a tiny list
of names that were actually supplied. Below the score threshold (0.60), or
when two names are equally close, the raw OCR string is kept and the field
is flagged low-confidence.

Street, house number, personnel, and names never go through this path.

Where the lists came from
-------------------------
The beneficiary-file table of contents and the DSD CW/COW pack have NO
place-name values for this NPO (only column headers named Province /
District). Training dummy towns in seed_data.py were not used.

The only geographic strings in the supplied Scan Intake material are the
handwritten cells on c01_household.jpg, as recorded in Phase 5:

  field          canonical     source
  -------------  ------------  ----------------------------------------------
  province       Gauteng       photograph / Phase 5 ('GAUTENG' on the cell)
  district       West Rand     photograph / Phase 5 (cell is West Rand;
                               synthetic round-trip ink was RANDWEST)
  town           Westonaria    photograph / Phase 5

Out of scope (no list supplied — raw OCR, no forced match)
  municipality
  ward           Phase 5 near-miss 'ern ee' is not close to any supplied
                 value. No ward list was in the pack or the contents page.

South Africa's nine provinces, Rand West City, Ward 32, and other
settlements were not added from general knowledge.
